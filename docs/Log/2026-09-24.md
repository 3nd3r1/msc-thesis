# 2026-09-24

## Pivot: entity-aware cascades instead of graph cardinality estimation

Narrowed the topic to entity-aware cascades for semantic filters. Writeup in
[Entity-aware cascades for semantic filters](../Directions/Entity-aware%20cascades%20for%20semantic%20filters.md).

The correlation insight is unchanged: rows of the same entity tend to get the same LLM
verdict. What changed is the use. Before, improve cardinality estimation for LLM filters in
graph pattern queries against the SemCEB gap [@zimmererSemCEBCardinalityEstimation2026].
Now, spend the oracle budget per entity inside a model cascade and settle an entity's
remaining rows from the verdicts already confirmed in it.

Why: the cascade has a metric comparable to existing work (oracle calls at a fixed accuracy
target), concrete baselines (LOTUS cascade [@lotus], CSV [@csv], Two-Phase
[@kimFastLLMBasedSemantic2026]), and it extends code that exists in LOTUS. Cardinality
estimation over graph patterns needed more machinery to say anything measurable. Graph
edges are now an extension, an entity key being a one-hop relationship.

## Consequences for experiment 01

Still the go/no-go on within-entity correlation, but it now has to cover all three risks:

- correlation within product IDs, as before
- the same measurement for embedding clusters, to show the entity key adds something
  embeddings do not already capture
- the entity-size distribution, since entities with 2-3 rows are too small to sample and
  vote on

It should also record token logprobs while labelling, so the labelled set is reusable
offline for later comparisons and for the Bayes-error difficulty measure.
`../../experiments/01_entity_correlation/run.py` predates the pivot and covers only the first.
